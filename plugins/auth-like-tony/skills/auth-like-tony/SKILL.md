# Auth, Tony's way

One recipe, reused across projects: **an admin panel that a short list of people
sign in to with a link sent by email.** Nothing else. No passwords to reset, no
OAuth apps to register, no sign-up page to abuse. If a project needs public user
accounts, this recipe is the wrong one; say so and stop.

Read this file, then pull the code from [references/code.md](references/code.md)
as you build each piece. The code comes from a working Next.js 16 project, with
the project-specific parts marked; copy it, rename, and keep the comments, they
explain the decisions to the next reader.

## The decisions, and why

- **Better Auth, magic-link plugin only.** It owns the tables, the session
  cookie, token hashing and the `/api/auth/*` routes. We add one plugin and one
  hook. Resist adding email+password "just in case": every extra method is an
  extra attack surface for a panel three people use.
- **Admins are the addresses in `ADMIN_EMAIL`**, comma-separated. That list is
  the whole user directory. An address on the list gets its account on first
  sign-in; taking an address off the list locks that person out on their next
  request, because `getSession()` re-checks the list every time. No roles table,
  no admin flag to forget to set.
- **The list is enforced in three places**, on purpose:
  1. `sendMagicLink` sends nothing to an address that is not on the list, and
     the form shows the same "if this is a panel account, we sent a link"
     message either way, so nobody can probe which addresses are admins.
  2. Better Auth's `user.create.before` hook refuses to create any other user,
     in case another path ever reaches it.
  3. `getSession()` drops a session whose address has left the list.
- **`requireAdmin()` is called by every admin page and every server action
  itself.** The layout also calls it, but a server action can be invoked with
  no layout rendered at all, so the layout's check protects nothing but pages.
  This is the rule most often broken in review; check for it.
- **Rate limiting lives in the database** (`rate_limit` table, `storage:
  'database'`). On serverless every function instance has its own memory, so an
  in-memory counter counts nothing. It is enabled in production only, so local
  testing never trips it.
- **Email goes through nodemailer over SMTP**, one `sendEmail()` helper for the
  whole app. Development points at the machine's shared Mailpit
  (`127.0.0.1:1025`, no user or password). Production points at AWS SES's SMTP
  endpoint, but any SMTP works, which is the point: switching providers is an
  `.env` change. With `SMTP_HOST` empty, emails are printed to the server
  console, so a fresh clone runs without Mailpit installed.
- **One Mailpit for the whole machine, never one per project.** It runs as a
  background service (`brew services start mailpit`): SMTP on `127.0.0.1:1025`,
  inbox on `http://localhost:8025`, up from login and outliving any project's
  dev server. `pnpm dev` checks that it answers and starts the service if it
  does not, so nobody has to remember it. No project starts a Mailpit of its
  own or stops the shared one. See "Several projects at once".
- **Development mail carries `X-Tags: <project>`**, so the shared inbox can be
  filtered to one project (`tag:project` in its search, or the tag in its
  sidebar). `sendEmail()` adds the header only when `NODE_ENV` is
  `development`; production mail never has it.
- **A phone signs in over Tailscale with one switch.** `TAILSCALE_ENABLED=true`
  and `TAILSCALE_IP` in `.env` move Better Auth's `baseURL` to the computer's
  Tailscale address, so the link and the redirect after it work on the phone,
  while `localhost` stays trusted for the computer. Next 16 also needs that
  address in `allowedDevOrigins`, or the page loads on the phone but never
  hydrates. Off by default; reference section 15.
- **The tables are in the project's own Drizzle schema** (`schema/auth.ts`),
  migrated with the rest, never generated by Better Auth's CLI into a separate
  place. Column and table names follow what Better Auth's adapter expects
  (`user`, `session`, `account`, `verification`, `rate_limit`).
- **The panel and its login are outside the site's locale routing** and carry
  `X-Robots-Tag: noindex`. If the site is bilingual, the panel's language is a
  cookie, and the magic-link email is sent in the language the login page was
  shown in.

## Several projects at once

Any number of these projects can run side by side. What they share, and what
each keeps to itself:

- **Mail: shared.** Every project sends to `127.0.0.1:1025`, and every message
  lands in the one inbox at `http://localhost:8025`, tagged with the project
  that sent it. The inbox keeps Mailpit's default of the latest 500 messages,
  across all projects.
- **Starting and stopping: independent.** The service is normally already up
  (it starts at login); if not, the first `pnpm dev` to run starts it and the
  rest find it up. Stopping a project's `pnpm dev` leaves Mailpit running, so
  the projects still running keep their inbox. Stopping it is a deliberate,
  machine-wide `brew services stop mailpit`, never part of a script.
- **App port: one per project.** Each project has its own dev port, fixed in
  its `dev` script (`next dev --port 3001`) and in `BETTER_AUTH_URL`. The
  sign-in link is built from `BETTER_AUTH_URL`, and in a shared inbox the port
  is the only thing that says which app a link opens. With `--port` given, a
  busy port makes Next fail instead of moving to the next free one, where the
  links would no longer match.
- **Cookies: one prefix per project.** Cookies on `localhost` ignore the port,
  so `advanced.cookiePrefix` is the project's slug (see "Adapting").
- **Containers** send to `host.docker.internal:1025`. No compose file has a
  Mailpit service.
- **Production data: still the shared Mailpit.** Anything running on the
  machine is development, whatever data it runs on. A `dev:prod` script, or a
  rehearsal on a copy of production's database, sends to `127.0.0.1:1025`,
  tagged with the project like any other run, and never to SES: it sets the
  four SMTP variables itself, over whatever `.env.prod` holds. Reference
  section 2.

## Build order

Do these in order; each step is checkable before the next.

1. **Dependencies.** In the web app: `better-auth`, `nodemailer`,
   `@types/nodemailer` (dev). On the machine, once for every project:
   `brew install mailpit && brew services start mailpit`; skip it if another
   project already did. Known-good: `better-auth ^1.7`, `nodemailer 10`, Next 16,
   `drizzle-orm ^0.45`. Add `"nodemailer"` (and the Postgres driver) to
   `serverExternalPackages` in `next.config.ts`, or the bundler will try to
   pack it.
2. **Env.** Add the block from the reference to `.env.example` and fill `.env`:
   `BETTER_AUTH_SECRET` (`openssl rand -base64 32`), `BETTER_AUTH_URL` (on the
   project's own port), `SMTP_HOST/PORT/USER/PASSWORD`, `EMAIL_FROM`,
   `ADMIN_EMAIL`. In development `SMTP_HOST=127.0.0.1`, `SMTP_PORT=1025`, user
   and password empty. If the
   project keeps production values in `.env.prod` loaded with `env-cmd`, it
   must set all four SMTP variables, or they fall back to Mailpit's.
3. **Schema.** Add `schema/auth.ts` (five tables), export it from the schema
   index, generate and apply the migration with the project's normal commands.
4. **Email.** `lib/email/send.ts`: the pooled transporter, `adminEmails()`,
   `sendEmail()` with the console fallback and the development `X-Tags`
   header. Then the magic-link message in the
   project's email layout (plain text and HTML, both). Keep the copy short: what
   the button does, that the link works once, when it expires, ignore if not
   requested.
5. **Server.** `lib/auth.ts` (the `betterAuth()` config), `lib/auth-client.ts`,
   `app/api/auth/[...all]/route.ts`, and `lib/admin.ts` with `getSession()` and
   `requireAdmin()`. `nextCookies()` stays last in the plugins list; it is what
   lets server actions set the session cookie.
6. **Pages.** `/login` (redirects to the panel when already signed in; shows the
   form; `?error=` from a failed link shows "expired or already used"), the
   `(admin)/admin/layout.tsx` that calls `requireAdmin()` and is
   `force-dynamic`, and a sign-out button that calls `authClient.signOut()` then
   `router.push('/login'); router.refresh()`.
7. **Routing and headers.** Exclude `api`, `admin` and `login` from any locale
   middleware/proxy matcher. Add the `noindex` header for `/(admin|login)/:path*`.
8. **Scripts.** Root `package.json`: `"mail": "nc -z 127.0.0.1 1025 >/dev/null
   2>&1 || brew services start mailpit"` and `"dev": "pnpm mail; next dev
   --port <the project's port>"` (exact lines in the reference, section 2).
   Mailpit that has to be started by hand gets forgotten, and then the sign-in
   link goes nowhere; `pnpm dev` making sure the shared one is up is what
   keeps the local loop reliable. Moving a project off its own Mailpit:
   reference section 2.
9. **Try it.** `pnpm dev`, open `/login`, enter an address from `ADMIN_EMAIL`,
   open `http://localhost:8025`, search `tag:<project>`, click the link, land
   on `/admin`. Then enter an address not on the list: same message on screen,
   nothing in Mailpit. Then sign out and hit `/admin` directly: back to
   `/login`.
10. **Phone (optional).** Add the Tailscale switch from reference section 15
    when someone will test the panel on a phone. With it on and `pnpm dev`
    restarted, the link in Mailpit starts with `http://<tailscale ip>:<port>`
    and signs the phone in.

## Adapting to the project

- **Cookie prefix and mail tag**: `advanced.cookiePrefix` and the `X-Tags`
  value are both the project's slug, so two of these apps on `localhost` do
  not share cookies and their mail is told apart in the shared inbox.
- **Where `db` comes from**: the reference imports `db` and the tables from a
  workspace package (`@project/db`). In a single-app repo they come from
  `@/lib/db` and `@/db/schema`; nothing else changes.
- **Single language**: drop the locale cookie lookup in `sendMagicLink` and the
  `useTranslations` calls in the form; hardcode the copy.
- **Not Next.js**: the server pieces (`betterAuth()` config, `sendEmail`,
  schema) are framework-free. Only `nextCookies()`, `toNextJsHandler`, the
  `headers()`/`cookies()` calls and the pages are Next-specific.
- **Another mail provider**: only `.env` changes. If a provider offers an HTTP
  API instead of SMTP, still prefer its SMTP endpoint; it keeps `send.ts`
  untouched and Mailpit exercising the same code path as production.

## What not to do

- Do not add a password, OAuth or passkey method, an admin role column, or a
  sign-up page unless the user asks for public accounts, and then question
  whether this recipe still fits.
- Do not gate the panel only in the layout, or only in a proxy/middleware.
  Every action, every page, itself.
- Do not read the admin list once at startup into a constant; read
  `process.env.ADMIN_EMAIL` on every call so a config change takes effect
  without a deploy of the code.
- Do not let the form say whether an address is an admin. Same message,
  same timing, either way.
- Do not run Better Auth's `generate`/`migrate` CLI. The tables belong to the
  project's schema and its migrations.
- Do not store the magic-link token in plain text; `storeToken: 'hashed'` is
  there for a reason.
- Do not give a project its own Mailpit, ever: not in `pnpm dev`, not in a
  compose file, not for a run on production data, not on ports nobody else
  uses. There is no exception. Do not stop the shared one from a script either.
- Do not let a run on this machine send through SES, even one that loads
  `.env.prod`. Its mail goes to the shared Mailpit.
